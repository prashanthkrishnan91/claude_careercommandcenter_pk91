## 3. Addition 1: Offer Workbench (P1)

### Rationale

v2.1's P1 schema includes `applications` and `comp_benchmarks`, but offers themselves and the parallel modeling of competing offers have no home. The negotiation window is the highest-leverage moment of the entire job search — a single workflow improvement here is worth more than a year of pipeline tracking. It also needs to integrate cleanly with the Visa Decision Checklist's Gate 7 (employer sponsorship commitment) and trigger mandatory attorney review of sponsorship terms.

### Schema

```sql
offers (
  id, user_id NOT NULL,
  application_fk,
  company_fk, role_title,
  received_at,
  status[draft|received|negotiating|accepted|declined|expired|withdrawn],

  -- Compensation components (all nullable; populate what's offered)
  base_salary, base_currency,
  bonus_target_pct, bonus_structure_notes,
  equity_grant_value, equity_vest_schedule_notes,
  equity_refresh_notes,
  signing_bonus, signing_bonus_clawback_notes,
  relocation_package, other_comp_notes,
  benefits_summary,

  -- Visa-critical (these gate Visa Checklist Gate 7)
  visa_sponsorship_committed_bool,
  priority_date_retention_committed_bool,
  visa_sponsorship_terms_text,
  attorney_reviewed_at,
  attorney_reviewed_doc_ref,
  attorney_notes,

  -- Timing
  expiration_date,
  decision_due_by,

  notes,
  created_at, updated_at
)

offer_scenarios (
  id, user_id NOT NULL,
  offer_fk,
  scenario_name,
  assumptions[json],          -- e.g., year-1 stock price, bonus payout %, etc.
  total_comp_yr1,
  total_comp_yr4,
  delta_vs_current[json],     -- delta in base, bonus, equity, total vs. current role
  notes,
  created_at
)

counter_proposals (
  id, user_id NOT NULL,
  offer_fk,
  proposed_changes[json],     -- which fields, what asks, what justification
  rationale,
  supporting_benchmark_refs[], -- FK array to comp_benchmarks
  sent_at,
  response_at,
  response_summary,
  outcome[accepted|partially_accepted|rejected|countered|no_response],
  created_at
)
```

### Integration rules

- **Visa Checklist Gate 7** cannot transition to `complete` until the linked offer has `visa_sponsorship_committed_bool = true`, `priority_date_retention_committed_bool = true`, AND `attorney_reviewed_at IS NOT NULL`.
- The app refuses to mark an offer `accepted` while Gate 7 is incomplete.
- `offer_scenarios.total_comp_yr1` and `total_comp_yr4` are stored as snapshots, not formulas. The app does not become a calculator; user fills in computed values from a separate spreadsheet if they want.
- `counter_proposals` are sent externally (manual); the app tracks them, doesn't send them.

### Honest scope warning

The temptation here is to build a full compensation calculator with formulas, equity vesting curves, tax modeling, and Monte Carlo simulations of stock value. **Resist.** Scenarios store user-computed numbers. The user computes them in Excel/Sheets. The app is a record-keeping and decision-staging surface, not a financial modeling engine.

## 4. Addition 2: Skill Development Plans (P1)

### Rationale

v2.1 has `skills` and `skill_evidence` for taxonomizing what you've done. The Comparator generates `gap_reports` identifying what's missing. But there is no entity tracking deliberate work to close those gaps. Without this, gap reports become observations, not actions.

### Schema

```sql
skill_development_plans (
  id, user_id NOT NULL,
  skill_fk,

  gap_source[archetype_comparator|self_identified|interview_feedback|manager_feedback|reference_feedback],
  gap_report_fk,              -- optional FK if sourced from Comparator

  current_level_1_to_5,
  target_level_1_to_5,
  rationale,                  -- why this skill matters for target archetype(s)
  target_archetype_refs[],

  method[work_project|side_project|course|certification|reading|mentorship|teaching|other],
  method_details,
  estimated_hours,

  start_date, target_date,
  status[planned|in_progress|completed|paused|abandoned],
  abandon_reason,

  notes,
  created_at, updated_at
)

skill_development_progress (
  id, user_id NOT NULL,
  plan_fk,
  progress_date,
  notes,
  linked_achievement_fk,      -- when progress yields a logged achievement
  hours_invested,
  level_assessment_1_to_5,
  assessed_by[self|peer|manager|external],
  created_at
)
```

### Integration rules

- A `skill_development_plan` may originate from a `gap_report` (Comparator), in which case `gap_report_fk` is set.
- When `skill_development_progress.linked_achievement_fk` is populated, the achievement counts as evidence of progress on that skill — feeds back into `skill_evidence`.
- Plans in `status = abandoned` are retained; abandonment reasons are valuable signal (over-ambitious, no longer relevant, blocked by external factors).
- Monthly Board Review surfaces stale `in_progress` plans (no progress entries in 60+ days).

### Honest scope warning

This is not a learning management system. No course catalog. No reading list manager. No habit tracker. Plans are skeletal records of intent + method + progress. The actual studying / project work happens outside the app.

## 5. Addition 3: References (P1)

### Rationale

Senior hires require references. The application that doesn't think about this until offer stage will scramble. Director-level references must be cultivated *before* the search activates, briefed on the candidate's current narrative, and maintained as relationships rather than activated cold.

### Schema

```sql
references (
  id, user_id NOT NULL,
  contact_fk,                 -- existing P1 contacts entity

  reference_type[manager|skip_level|peer|direct_report|executive|client|external_partner|other],
  employer_at_time,           -- where they worked with you
  working_relationship_period_start,
  working_relationship_period_end,
  relationship_summary,
  strongest_themes[json],     -- e.g., "scope of analytics leadership", "cross-functional influence"

  willingness_status[unconfirmed|confirmed|tentative|declined|do_not_ask],
  willingness_confirmed_at,
  willingness_notes,

  last_briefed_at,            -- when did they last hear your current narrative
  current_narrative_version_fk,  -- which positioning_statement asset they're briefed on
  briefing_method[in_person|video_call|email|li_message|other],

  cadence_target_months,      -- e.g., touch base every 6 months
  last_touch_date,
  next_touch_due,

  used_for_application_refs[], -- when they've been used as a reference

  notes, created_at, updated_at
)
```

### Integration rules

- A `reference.contact_fk` must point to an existing `contact`. References are a status overlay on contacts, not a separate identity.
- `willingness_status = do_not_ask` is honored permanently; the app never surfaces this person as a reference candidate.
- Monthly Board Review surfaces references where `last_briefed_at` is older than the latest positioning_statement version — these need re-briefing before next use.
- References cannot be used in an application (`used_for_application_refs`) until `willingness_status = confirmed`.

### Honest scope warning

- The app does not ask references on your behalf. All willingness conversations happen externally; the app records the outcome.
- The app does not send briefing material to references. Narrative briefing is a human conversation; the app tracks when it last happened.
- Privacy: `contacts.notes` and `references.notes` may contain sensitive personal observations. These remain at the user's privacy_class of choice; defaults to INTERNAL_ONLY and never enters external assets.

## 6. Cross-Reference Map

How v2.2.1's three additions connect to v2.1's existing entities:

```
offers
  ├── application_fk → applications (P1)
  ├── company_fk → companies (P1)
  ├── visa fields → triggers visa_checklist_items Gate 7 (P0F)
  └── supporting_benchmark_refs → comp_benchmarks (P1)

skill_development_plans
  ├── skill_fk → skills (P0/P1 boundary, defined in v2.1)
  ├── gap_report_fk → gap_reports (P0D)
  ├── target_archetype_refs → target_archetypes (P0D)
  └── linked_achievement_fk → achievements (P0A)

references
  ├── contact_fk → contacts (P1)
  └── current_narrative_version_fk → asset_versions (P0E)
```

All three additions integrate cleanly with existing entities. No refactoring of v2.1 schema is required.
