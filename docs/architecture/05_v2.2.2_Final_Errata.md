## 2. Correction C1 — Narrow P0A Settings

### What v2.2 said
v2.2 §4 listed the Settings panel as containing: "profile, defaults, data export, RLS audit log."

### What v2.2.2 corrects it to

**P0A Settings contains only:**

- **Profile placeholder** — name, target role (free text, not yet linked to archetypes), nothing else
- **Default truth status** for new entries (default: `NEEDS_PROOF`)
- **Default privacy class** for new entries (default: `INTERNAL_ONLY`)
- **Static privacy/RLS explanation** — a read-only paragraph explaining what privacy classes mean, what RLS guarantees, and that this is a single-user system with all data scoped to the authenticated user

### Explicitly deferred from P0A Settings

- Data export (any format — JSON, CSV, archive)
- RLS audit log UI
- OAuth / token management
- Advanced account controls (rotation, session management, deletion)
- Theme switching
- Notification preferences
- Anything resembling an admin console

### Rationale

P0A must prove that evidence capture and vault usability work. Settings is not the surface that earns that proof. Real data export becomes meaningful when there's a meaningful amount of data and a real reason to export it. RLS audit becomes meaningful when there's data access worth auditing. Both are real engineering work that distracts from the P0A core question: *does the evidence vault feel like a serious cockpit during real backfill?*

### Schema impact

None. P0A Settings is a UI surface only; no new tables.

## 3. Correction C2 — Future-Surfaces Footer Made Optional

### What v2.2 said
v2.2 §4 and §7 specified a "future-surfaces footer strip" on the achievement detail page, indicating where Grader, Sanitization, and Asset references will eventually appear.

### What v2.2.2 corrects it to

The future-surfaces footer **may** be included in P0A only if all three conditions hold:

1. It is visually quiet — small text, low contrast, no boxes/borders/badges drawing attention
2. It is clearly labeled "planned later" or equivalent neutral language (not "coming soon," not animated, not styled as a feature preview)
3. It does not create clutter, confusion, or vaporware feel when the user is in the middle of backfill flow

**If any of those three conditions fails, remove the footer from P0A.** The cockpit aesthetic is served by either a clean, restrained future-surfaces strip *or* its absence — but never by a footer that looks like broken or unfinished UI.

### Default recommendation

**Default to omitting the footer in P0A.** Add it only if, during build, it can be implemented cleanly in under an hour and reads as quiet supplementary metadata. If it requires design iteration to "get right," skip it — its value is small.

The detail page works without it. Future slices (P0C grader, P0E generator, P0B sanitization) will introduce their own surfaces in the natural locations on the achievement detail page when their functionality lands.

### Rationale

The footer was proposed in v2.2 as a way to convey cockpit shape on day one. On reflection, the risk of vaporware feel is real, and the cockpit shape is conveyed sufficiently by the typography, density, and information layout already specified. The footer is a nice-to-have, not a necessary signal.
